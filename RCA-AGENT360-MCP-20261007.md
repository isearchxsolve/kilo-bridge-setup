# RCA: Agent360 Browser MCP appeared disconnected

**Date:** 2026-10-07  
**Scope:** `C:\Users\Admin\Downloads\kilo-bridge-setup`, OpenCode CLI and Agent360 browser extension.

## Finding

The observed issue was not a persistent MCP registration or transport outage. The popup's
**Not connected** state appeared when no active OpenCode browser-tool session owned the
on-demand local WebSocket bridge. During active runs the bridge was available. A separate
agent instruction defect then caused an avoidable page-script error while inspecting a
profile field.

## Evidence from the run

- `opencode mcp list` reported `browser-mcp` connected to installed Agent360 Browser MCP
  version 1.30.0.
- The first `browser_list_tabs` request returned `Unknown` once. The agent's subsequent
  `browser_navigate` succeeded, and its `browser_screenshot` saved
  `evidence\employment-lane\02-profile-screenshot-20261007.png`.
- While that OpenCode mission was active, TCP port 9876 was listening. The screenshot
  showed the authenticated Naukri profile in the intended Agent360 Chrome session.
- After the OpenCode process was stopped, there was no listener on ports 9876-9895 and the
  popup showed **Not connected**. This matches the bridge's on-demand lifecycle.
- In an earlier direct OpenCode call, `browser_list_tabs` returned an empty session-scoped
  list (`session: "Claude 1"`). Empty means no tabs owned by that Agent360 session yet; it
  does not establish that Chrome is signed out or that a different profile is needed.

## Why the agent errored

The mission agent later called `browser_execute_script` to inspect the visible phone field.
The tool failed with both a portal Content Security Policy `unsafe-eval` rejection and
`SyntaxError: Unexpected token ';'`. The page-content and screenshot tools had already
shown the relevant visible state, so page script execution was unnecessary. Older mission
text listed `browser_execute_script` for inspection and encouraged DOM/JS clicks, while a
separate paragraph prohibited form mutation. That ambiguity permitted the bad fallback.

The run was interrupted after the script error. No Save, submit, or OTP action occurred in
the observed run, and no server-side profile update is evidenced. An earlier interrupted
attempt also ended before a Save/OTP receipt; do not count profile changes as completed.

## Root-cause distinction

1. **Red popup when idle:** expected bridge lifecycle after the OpenCode session ended.
2. **One startup `Unknown`:** transient per-call/session warm-up failure; subsequent
   navigation and screenshot succeeded on the same session. This single error is not
   evidence of persistent MCP outage.
3. **Mission execution failure:** bad tool selection plus malformed JavaScript, rejected by
   the site's CSP. This is an agent-directive defect, not a browser-MCP connection failure.

## Corrective actions

- Removed `browser_execute_script` from the supported mission tool workflow and prohibited
  it for inspection and interaction.
- Changed startup to navigate to the requested portal, then screenshot and read page state;
  `browser_list_tabs` is no longer a startup prerequisite.
- A single `Unknown` is recorded and followed by one independent, low-risk navigation or
  screenshot. Continue only after a visible-page receipt; if both fail, block that lane.
- Profile edits remain visible-UI-only. If visible fill fails, retry once on the current
  session tab with a fresh screenshot, then mark BLOCKED without saving.
- Updated this diagnosis and the client-facing README with the distinction between idle
  badge, transient tool error, and actual browser-session failure.

This RCA and the directive changes are not proof that the employment E2E lanes passed.
The package is not ready to claim full E2E completion until every lane has fresh local
receipts and the exact required actions are visibly verified.

## Second launch reproduction (17:45-17:46 IST)

The next launch started after the first directive update. The model still called
`browser_list_tabs` first and received `Unknown`; it then navigated to Naukri and captured
`evidence\employment-lane\02-profile-screenshot-20261007.png`. This again confirms the
browser bridge worked after the tab-list error. The model then produced an extended
speculative narrative, treating image details and resume aggregates as sufficient proof of
profile mismatches and describing a click it had not actually performed. The run ended
without a further verified browser action, profile save, application, or ledger receipt.

This is a second defect: the model did not follow the startup sequence in the mission text
and did not maintain evidence-grounded reporting. I removed tab-list/switch/close tools from
the package's stated workflow and added explicit rules requiring a verified action receipt
before claiming a click/edit, and prohibiting inferences from unreadable screenshots or
resume aggregates. Since the model ignored prompt-level guidance, the fix now also uses a
project-local OpenCode primary agent with permission rules that deny those browser tools at
the OpenCode execution layer. The launcher explicitly selects that agent and fails the run
if the first two browser calls, fresh screenshot, fresh ledger entry, or report headings are
missing. OpenCode's resolver confirmed `browser-mcp_browser_*` is denied by default and only
the required visible-UI tools are allowed. This is stronger enforcement, but a full mission
run is still needed to validate the end-to-end behavior before shipment.
